# Follow-up Message Drafting

## Follow-up Message Principles

The follow-up is sent via LinkedIn DM after they accept the connection.

**Default: keep it short (2-4 sentences).** Link to the product page and offer a call. The connection note already did the framing work. A long follow-up immediately after acceptance looks automated and desperate. Let the product page do the heavy lifting.

**Go longer (up to 150 words) only when:** there's specific context from the acceptance to build on (e.g., they replied with a question, they posted something relevant, or you have a warm intro to reference). The length should be earned by context, not used by default.

### Tone & Style

- **Write like a founder, not a marketer.** Short sentences. Direct language. No fluff.
- **No em-dashes (--).** Use periods, commas, or restructure the sentence instead.
- **No label-colons.** Don't use colons as setup for a punchline or label (e.g., "The gap: proving footage..."). Restructure into a flowing sentence.
- **No AI-typical phrases:** "I hope this finds you well", "I'd love to connect", "excited to share", "revolutionizing", "cutting-edge", "leveraging", "synergy"
- **No cringe words:** "nailed", "resonated", "literally", "invaluable"
- **No excessive politeness or hedging.** Be direct but respectful.
- **No bullet point lists.** Write in natural paragraphs.
- **Keep it conversational.** Read it out loud. If it sounds like a press release, rewrite it.

### Varying the Opening

Do NOT always open with the same hook. The opening must match the audience type and feel distinct from other messages in the same batch.

**Opening strategies (rotate):**

1. **Question opener** (use sparingly, only when the question is genuinely interesting to the recipient).
2. **Vulnerability opener** (Type A problem-holders): name a specific failure mode in their stack that you can address.
3. **Observation opener** (shows you read their work): reference something specific they said publicly.
4. **Story opener** (Type C journalists): lead with a milestone or angle that has narrative weight.

### Price Placement

If your project has a memorable price point, it can be a powerful detail, but becomes a template signature when it always appears in the first sentence. Weave it in wherever natural; sometimes opening, sometimes third paragraph, sometimes only in a link. **Never include internal cost data (BOM, margin) in outreach.**

|----------|----------------------|

| Standards people | reference specific spec versions and conformance requirements |
| Non-English locales | translate the outcome, not the spec |

### AI Disclosure

Context-dependent, not mandatory.

**Include when:** the recipient works in trust, authenticity, or journalism; transparency about drafting tools aligns with your brand. Phrasing can vary:
- "Drafted with AI, research and decision to reach out are mine."
- "Used AI for drafting; the research is mine."

**Omit when:** the receiver context makes it awkward (e.g., short connection notes with no room, recruiters / HR contacts where it's irrelevant, locales where AI-disclosure norms differ).

If omitted, inform the user so they can add it back if preferred.

### Sign-off format

```
Founder
[Your Project]
founder@yourproject.example
```

Keep it simple. NOT "Co-founder & CEO, [Project]". For non-English messages, match the locale's sign-off convention.

### Length

- **Default: 2-4 sentences.** Link + offer a call. Don't repeat the connection note.
- **Extended (up to 150 words):** Only when context justifies it.
- **Never exceed 200 words.** If it's longer, cut.

### Positioning Rules

1. **Complement, not compete** (Type A and B only). For journalists and academics, this framing is irrelevant; don't force it.
2. **Be honest about stage.** Don't undersell ("just prototyping") or overclaim ("already shipping"). Cite specific, public milestones.
3. **No unconfirmed partnerships.** Reference only those the user has explicitly approved.
4. **Sell the thing you actually sell.** Don't dangle business models that aren't your current model.
5. **Never propose integration architectures in first contact.** Ask for a conversation, not a commitment.
6. **Never ask for pilot commitments in first contact.** "Would this be relevant to explore?" not "Would you be open to piloting with us?"

### Technical Explanation of the Product

When explaining the product, adapt to the audience type. Keep it to 2-3 sentences. Don't list every feature unless it's specifically relevant to the recipient's documented concerns. Maintain a project-specific "core facts" list (kept in your own private notes, not in this public skill) and draw from it with vocabulary appropriate to the audience.

## Quality Checklist (follow-up message)

Before presenting the final output, verify:

**Follow-up message (when drafting separately after acceptance/reply):**
- [ ] Under 200 words?
- [ ] No em-dashes, label-colons, cringe words, AI phrases?
- [ ] Hook references specific work by the recipient?
- [ ] Honest about stage?
- [ ] Sign-off matches the locale and your project's convention?
- [ ] Would a real founder actually send this?
- [ ] No duplicate CTAs or duplicate ideas across paragraphs?
- [ ] Technical vocabulary matches the recipient's background?
- [ ] AI disclosure included / omitted per context rules?

## Reference Links

Maintain a project-specific link table (kept in your own private notes or in a separate skill, not in this public file) covering:

- Main site
- Product / pricing page
- Locale variants
- Blog posts you can cite for specific claims
- Whitepapers / PDFs
- Independent validation (academic papers, conference talks, third-party benchmarks)
- Demo videos, tagged by audience type

Drafting rules:
- Only include a link if it directly supports a claim in the message.
- Don't dump multiple links.
- Do NOT include links in connection notes (they don't render well and waste characters).
- **Always include `https://` prefix.** LinkedIn does not hyperlink bare domains.

### What to Cut

If the follow-up is too long, remove in this order:

1. Analogies and metaphors
2. Repeated attack vector lists
3. Excessive technical detail beyond what's needed for the hook
4. Formal transition phrases ("Furthermore", "Additionally", "In this context")
5. Any sentence that restates something already said
